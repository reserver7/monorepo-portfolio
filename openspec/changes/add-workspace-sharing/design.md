## Context

현재 계정 소유권은 목록·생성·삭제에 적용되어 있고, 문서·화이트보드 상세 및 실시간 방은 기존 세션과 보호 키 계약을 사용합니다. 이번 변경은 이 경계를 계정 멤버십까지 확장하되, 기존 시스템 소유 레코드는 깨뜨리지 않아야 합니다.

## Goals / Non-Goals

**Goals:**

- 개인 레코드를 비공개 기본값으로 보호합니다.
- 이메일 기반 멤버와 `viewer`/`editor` 역할을 저장하고 검사합니다.
- HTTP 상세 API와 WebSocket 방 참여에 같은 권한 판정을 적용합니다.
- 파일/Supabase JSONB 상태를 재사용하고 기존 레코드를 읽을 수 있게 합니다.

**Non-Goals:**

- 공개 링크와 익명 게스트 공유
- 조직, 팀, 그룹, 도메인 기반 자동 초대
- 별도 Supabase Auth 또는 사용자 디렉터리 구축
- 휴지통·복구·알림 기능

## Decisions

### 1. 레코드 내부 ACL 저장

문서와 화이트보드 레코드에 `visibility`, `members`를 nullable 필드로 추가합니다. 멤버는 `{ accountId, email, role, invitedAt }`로 저장하고, 요청 시 `accountId`와 정규화된 이메일을 함께 비교합니다.

별도 ACL 테이블 대신 현재 JSONB 상태 저장 구조를 유지합니다. 이번 기능의 최소 변경이며 Supabase와 파일 저장 간 동작 차이를 만들지 않습니다. 데이터 규모가 커지면 레코드 테이블과 멤버 테이블을 분리합니다.

### 2. 권한 판정 단일화

HTTP와 WebSocket이 각각 권한을 구현하지 않도록 `owner`, `editor`, `viewer`, `denied`를 반환하는 서버 권한 판정 함수를 둡니다. 소유자는 항상 전체 권한을 가지며, 멤버 역할은 레코드에 저장된 이메일과 계정 ID가 모두 일치할 때만 인정합니다.

### 3. 세션 전달

Collab 웹의 서버 프록시는 기존 HttpOnly 쿠키를 이용해 HTTP 요청에 세션을 전달합니다. 실시간 연결은 브라우저에 브리지 비밀값을 노출하지 않고, 서버가 발급한 제한된 세션 토큰만 연결 인증에 사용합니다. 토큰이 없거나 검증되지 않으면 방 참여를 거부합니다.

### 4. 기존 레코드 판정

`ownerId`와 ACL이 모두 없는 레코드는 기존 시스템 레코드로 취급합니다. 이 레코드에만 기존 보호 키·게스트 흐름을 허용하고, 새로 생성되는 개인 레코드는 반드시 소유자 ACL을 가집니다.

### 5. UI는 상세 화면의 공유 패널로 제한

새 전용 관리 화면을 만들지 않고 문서·화이트보드 상세 화면에 공유 패널을 추가합니다. 소유자에게만 이메일 초대, 역할 변경, 멤버 제거 UI를 표시하고, 멤버에게는 현재 권한과 읽기 전용 상태를 표시합니다.

## Risks / Trade-offs

- [Risk] 이메일 변경이나 계정 병합 시 이메일 기반 초대가 오래된 상태가 될 수 있습니다. → 계정 ID가 있으면 ID를 우선하고 이메일은 초대 생성·표시용 보조 정보로 사용합니다.
- [Risk] 기존 WebSocket 클라이언트가 새 인증 정보를 보내지 않을 수 있습니다. → 단계적으로 서버가 인증 없는 연결을 기존 레코드에만 허용하고, 새 개인 레코드는 인증을 필수로 합니다.
- [Risk] 전체 JSONB payload 동시 저장은 멤버 변경 충돌을 만들 수 있습니다. → 기존 저장 직렬화 경로를 재사용하고, 충돌 시 최신 상태를 다시 읽어 UI에서 재시도하게 합니다.

## Migration Plan

1. nullable ACL 필드를 읽을 수 있는 서버를 먼저 배포합니다.
2. 새 레코드 생성 시 owner ACL을 저장하고 상세·실시간 권한 검사를 활성화합니다.
3. 기존 레코드는 시스템 레코드로 유지하며 운영 로그와 기본 공유 흐름을 확인합니다.
4. 문제가 생기면 ACL 검사 이전 버전으로 롤백할 수 있도록 새 필드는 무시 가능한 형태로 유지합니다.
