## Context

현재 Collab 서버는 문서·화이트보드 전체를 메모리 Map으로 관리하고 파일 또는 Supabase JSONB 상태로 저장합니다. Collab 웹은 HttpOnly 세션 쿠키를 보유하지만 브라우저에서 직접 호출하는 기존 API에는 계정 식별자 경계가 없습니다. 상세 방의 실시간 편집은 기존 보호 키와 세션 계약을 사용하므로 이번 변경에서는 목록·생성·삭제의 소유권을 먼저 분리합니다.

## Goals / Non-Goals

**Goals:**

- OpsLens 세션에서 계정 식별자를 안전하게 얻습니다.
- 생성·목록·삭제를 계정 기준으로 제한합니다.
- 파일 저장과 Supabase JSONB 저장 양쪽에서 소유자 필드를 보존합니다.
- 기존 시스템 레코드와 보호 키 기반 방 접근을 깨뜨리지 않습니다.

**Non-Goals:**

- 팀 초대, 공유 링크, 역할별 협업 권한 변경
- 실시간 WebSocket 메시지마다 사용자 계정 권한을 재설계하는 작업
- Supabase Auth로 인증 체계를 다시 만드는 작업

## Decisions

### 1. OpsLens 서명 세션을 계정 식별자의 원천으로 사용

Collab 서버는 기존 `AUTH_BRIDGE_SECRET`으로 세션 토큰의 서명을 검증하고 토큰의 사용자 ID를 사용합니다. 클라이언트가 보내는 `ownerId`는 신뢰하지 않습니다. 별도의 인증 시스템이나 사용자 테이블을 추가하지 않아 OpsLens와 계정이 계속 단일화됩니다.

대안으로 Supabase Auth를 추가할 수 있지만 현재 제품의 인증과 계정이 분리되고, 사용자가 두 번 로그인해야 하므로 선택하지 않습니다.

### 2. 소유권 API는 Collab 웹 서버 프록시를 통해 호출

HttpOnly 세션 쿠키를 브라우저 JavaScript에 노출하지 않기 위해 Collab 웹의 서버 라우트가 쿠키를 읽고 Collab 서버에 검증된 세션 토큰을 전달합니다. 계정별 목록·생성·삭제 클라이언트 API는 이 same-origin 프록시를 사용합니다. 상세 방과 실시간 편집 API는 기존 흐름을 유지합니다.

### 3. 기존 상태는 nullable ownerId로 점진 호환

저장 레코드의 `ownerId`는 기존 데이터에 없을 수 있으므로 nullable로 읽고 씁니다. 새 레코드에는 반드시 값이 들어가며, 누락된 레코드는 `system` 소유로 간주합니다. 별도의 대규모 데이터 변환 없이 파일과 Supabase JSONB 양쪽에서 같은 형태를 사용합니다.

### 4. 삭제 권한은 소유자 우선, 레거시에는 기존 보호 키 유지

소유자는 자신의 레코드를 삭제할 수 있습니다. 타인 소유 레코드는 403으로 차단합니다. 소유자가 없는 시스템 레코드는 기존 editor access key 검증을 거쳐야 하므로 기존 사용자 데이터의 운영 방식을 보존합니다.

## Risks / Trade-offs

- [Risk] 기존 시스템 레코드는 모든 인증 사용자에게 보일 수 있습니다. → 레거시 호환을 위해 목록에 표시하되, 후속 공유/마이그레이션 기능에서 명시적 소유자로 전환합니다.
- [Risk] 목록·생성·삭제와 상세 방의 인증 경계가 당분간 다릅니다. → 이번 변경에서 범위를 문서화하고, 다음 단계에서 WebSocket 세션에 계정 ID를 연결합니다.
- [Risk] JSONB 전체 상태에 필터링된 레코드를 저장하면 동시 사용자 확장성이 제한됩니다. → 현재 단일 상태 저장 구조를 유지하고, 사용자 수나 상태 크기가 커질 때 테이블 분리 마이그레이션을 진행합니다.

## Migration Plan

1. 서버와 웹을 함께 배포하여 nullable `ownerId` 읽기를 먼저 활성화합니다.
2. 새 생성 요청부터 소유자를 기록하고 계정별 목록 필터를 적용합니다.
3. 운영 헬스체크와 기본 CRUD를 확인합니다.
4. 롤백 시 새 필드를 무시하는 이전 서버로 되돌릴 수 있으며, 기존 레코드 데이터는 유지됩니다.
