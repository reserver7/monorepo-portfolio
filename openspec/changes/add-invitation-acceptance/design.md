## Context

현재 멤버는 문서·화이트보드 레코드 안에 저장되고 `resolveWorkspacePermission`이 이메일 또는 계정 ID로 역할을 판정합니다. 초대 이메일은 작업 공간 URL을 직접 가리키므로, 초대를 pending으로 바꾸려면 접근 판정과 링크 목적지를 함께 변경해야 합니다.

## Goals / Non-Goals

**Goals:**

- 멤버 상태를 저장하고 수락·거절 API를 제공한다.
- pending·declined 멤버가 접근하지 못하도록 HTTP와 WebSocket 권한 판정을 동일하게 유지한다.
- 문서와 화이트보드에서 동일한 초대 화면과 응답 흐름을 재사용한다.

**Non-Goals:**

- 초대 만료, 재전송, 감사 로그, 별도 초대 토큰 발급은 이번 변경에 포함하지 않는다.
- 기존 멤버 데이터를 일괄 마이그레이션하지 않는다.

## Decisions

- `WorkspaceMember`에 선택적 `status`와 `respondedAt`을 추가한다. 상태가 없는 기존 데이터는 accepted로 해석해 기존 공유를 깨지 않는다.
- 응답 API는 계정 세션에서 대상 이메일을 확인하고 요청 본문의 이메일을 신뢰하지 않는다. 초대 대상 외 계정의 응답을 차단한다.
- 수락·거절 엔드포인트는 문서와 화이트보드 멤버 리소스 아래에 두고, 웹 프록시도 동일한 경로를 전달한다.
- 이메일 링크는 kind, entityId를 포함하는 웹 초대 페이지로 연결한다. 별도 토큰은 현재 인증 브리지와 중복되므로 추가하지 않는다.

## Risks / Trade-offs

- [Risk] 이메일만 같고 아직 계정 ID가 연결되지 않은 pending 초대는 계정 생성 후에만 응답할 수 있다. → 응답 시 계정 ID를 저장하고 이후 계정 ID를 우선 사용한다.
- [Risk] 이메일 링크가 노출되면 작업 공간 식별자가 드러날 수 있다. → 실제 권한 변경은 인증 계정 이메일 일치와 서버 권한 판정으로 보호한다.
- [Risk] 상태 필드가 없는 과거 데이터가 존재한다. → undefined 상태를 accepted로 처리한다.

## Migration Plan

코드 배포만으로 적용한다. 기존 JSON/Postgres 레코드는 수정하지 않고 읽을 때 accepted로 해석하며, 새 초대부터 상태를 저장한다. 롤백 시 새 필드는 optional이므로 이전 코드도 기존 레코드를 읽을 수 있다.
